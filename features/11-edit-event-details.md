## Goal

Organisers need the ability to edit event fields after creation — change the time, update the location, add notes, fix a typo. Attendees who have already RSVP'd should see that the event details have been updated.

## Implementation Notes

### What was built

1. **Schema** (`packages/db/src/schema.ts`): Added `last_edited_at` integer (timestamp) column to the `events` table. This records when an organiser last changed event details.

2. **Migration** (`packages/db/drizzle/0001_kind_jane_foster.sql`): Drizzle-generated ALTER TABLE adding the `last_edited_at` column.

3. **Core helpers** (`packages/core/src/edits.ts`):
   - `isWithinNotificationWindow(lastEditedAt, now)` — pure function: is the edit recent enough to page confirmed attendees (1-hour window)? Handles null/undefined/future timestamps.
   - `relativeAge(timestamp, now)` — coarse human-friendly age bucket ("just now", "minutes", "hours", "days") used on the event detail page.
   - Exported via `packages/core/src/index.ts`.

4. **Update server action** (`apps/web/src/lib/actions/update-event.ts`):
   - `"use server"`, auth-gated, ownership-checked (only `ownerId` may edit).
   - Accepts date/time/location/notes/typeTag. Sets `lastEditedAt` to `new Date()`.
   - Enqueues a `jobs` row of type `event_edited` when `isWithinNotificationWindow` returns true (edit within the last hour).

5. **Event detail page** (`apps/web/src/app/events/[id]/page.tsx`):
   - Server component showing all event fields (date, time, location, notes, type tag).
   - "Last edited" indicator with relative age ("Details updated just now" / "in the last hour" / "earlier today" / "recently").
   - RSVP count summary (in/out) derived from the `rsvps` table.
   - "Edit" button for the owner linking to `/events/[id]/edit`.
   - For non-owner viewers: an attendee change indicator message when `lastEditedAt` is set.
   - Auth-gated with redirect to `/login`.

6. **Edit form page** (`apps/web/src/app/events/[id]/edit/page.tsx` + `edit-event-form.tsx`):
   - Server-rendered page checks auth and ownership; redirects non-owners to the detail page.
   - Client form with `useActionState`, prefilled from existing DB values.
   - Fields: date, time, location, notes, type tag.
   - On success, redirects back to the event detail page.

7. **Worker handler** (`apps/worker/src/index.ts`):
   - Registered `event_edited` job handler with a documented TODO contract.
   - Currently logs the event; the real WhatsApp fan-out will be implemented when Meta credentials are available (Milestone 4).

8. **Pre-existing fixes**:
   - Fixed `useActionState<State, Payload>` two-generic type inference in both `event-form.tsx` and `edit-event-form.tsx`.
   - Added `drizzle-orm` and `better-sqlite3` as direct dependencies of `apps/web` for `serverExternalPackages` resolution.
   - Added `drizzle-orm` as a dependency of `apps/worker`.
   - Fixed the pre-existing worker `Transaction` type error (`sqlite.transaction(fn)` must be invoked).

### RSVP change indicator limitation

The AC "Attendees see a subtle indicator that event details have changed since they RSVP'd" is partially met. Since RSVP UI does not yet exist (only the `rsvps` table and its unique constraint), there is no per-viewer "seen at RSVP time" marker to compare against. Instead:

- **All viewers** (both owner and attendees) see the "Details updated <relative time>" line when `lastEditedAt` is set.
- **Non-owners** additionally see a persistent banner: "Event details have changed since this event was created."
- When RSVP UI lands in a future milestone, a per-user `lastSeenEditAt` column on `rsvps` or a dedicated `event_seen` table can provide the exact "changed since you RSVP'd" behavior.

### Notification hook limitation

The notification job (`event_edited`) is enqueued with a durable `jobs` row but the worker handler only logs — it does not fan out WhatsApp messages. This requires Meta WhatsApp credentials that are not available in this environment. The handler has a detailed TODO comment describing the expected implementation.
